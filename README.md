# Harry Potter Explorer

**Живая версия: [http://2.29.26.110](http://2.29.26.110)** · **Исходный код: [github.com/msultans/harry-potter-explorer](https://github.com/msultans/harry-potter-explorer)**

Веб-приложение для изучения волшебного мира: факультеты Хогвартса, 437 персонажей с поиском и фильтрами, 77 заклинаний и 23 легендарных артефакта. Данные о персонажах и заклинаниях берутся из [Harry Potter API](https://hp-api.onrender.com/), но **браузер к нему не обращается ни разу** — все внешние вызовы идут через собственные серверные маршруты приложения.

Дополнительно реализованы все четыре бонусных пункта: подробная карточка персонажа, избранное в `localStorage`, выгрузка данных в Supabase с лентой событий в реальном времени и разговор с персонажами через языковую модель. Модель запускается локально через [Ollama](https://ollama.com) — в проекте нет ни одного платного ключа и ни одного обращения к стороннему сервису языковых моделей.

## Технический стек и почему именно он

**Next.js 16 (App Router) + TypeScript.** Главное требование задания звучит так: внешние сервисы вызываются только с серверной стороны. В Next.js это не отдельная работа, а свойство фреймворка. Серверные компоненты выполняются исключительно на сервере, а маршруты в `app/api/*` дают собственный HTTP-интерфейс поверх внешнего API. Альтернатива в виде отдельных фронтенда и бэкенда потребовала бы двух приложений, настройки CORS и двух деплоев ради той же цели.

Строгий режим TypeScript выбран потому, что источник данных сообществом поддерживается неаккуратно: у 302 персонажей из 437 пустой факультет, у 412 нет изображения, длина палочки бывает `null`. Типы вынуждают обрабатывать эти случаи в коде, а не ловить их в браузере.

**Tailwind CSS v4.** Оформление задаёт настроение и должно быть единым на всех страницах. Токены темы (`night-*`, `gold-*`, `parchment`) объявлены один раз в `app/globals.css` через директиву `@theme`, а повторяющиеся элементы вынесены в классы `.card`, `.btn-gold`, `.chip`. Отдельный файл настройки в четвёртой версии не нужен, вся тема живёт в CSS.

**React 19 без внешнего менеджера состояния.** Состояние приложения делится на три независимых части: серверные данные, параметры каталога и избранное. Первую держит кеш Next.js, вторую — строка запроса в URL, третью — `localStorage` через `useSyncExternalStore`. Ни одна из них не выигрывает от Redux или Zustand, поэтому лишних зависимостей нет.

**Ollama как единственный провайдер языковых моделей.** Задание разрешает любого провайдера. Выбор пал на Ollama по трём причинам. Во-первых, модель работает на нашем собственном сервере, поэтому требование «внешние сервисы вызываются только с серверной стороны» выполняется предельно строго: стороннего сервиса просто нет. Во-вторых, проект можно развернуть и показать без единого платного ключа, что важно для учебной работы. В-третьих, Ollama помещается в тот же `docker compose`, что и приложение, поэтому весь стек поднимается одной командой.

Используется нативный HTTP-интерфейс Ollama, а не его OpenAI-совместимая надстройка: нативный API дополнительно сообщает список установленных моделей, и благодаря этому интерфейс может точно объяснить, чего именно не хватает, вместо общей ошибки.

**Supabase.** Требовалась база с просмотром в реальном времени. Supabase даёт PostgreSQL, готовую панель и репликацию изменений без собственного сервера.

Внешняя зависимость сверх самого фреймворка ровно одна — клиент Supabase, и та нужна только для бонусной ленты реального времени. Общение с моделью реализовано обычными запросами `fetch`, без дополнительного SDK.

## Установка и запуск

Требуется Node.js версии 20.9 или новее.

```bash
git clone https://github.com/msultans/harry-potter-explorer.git
cd harry-potter-explorer
npm install
npm run dev
```

Приложение откроется на `http://localhost:3000`. Никаких ключей для этого не нужно: главная, факультеты, каталог персонажей, заклинания, артефакты и избранное работают сразу.

Остальные команды:

```bash
npm run build      # production-сборка
npm start          # запуск собранного приложения
npm run typecheck  # проверка типов
npm run lint       # проверка стиля
```

## Переменные окружения

Все переменные необязательные. Шаблон лежит в `.env.example`, для локальной работы скопируйте его в `.env.local`.

| Переменная | Назначение |
|---|---|
| `HP_API_BASE_URL` | адрес Harry Potter API, по умолчанию официальный |
| `OLLAMA_BASE_URL` | адрес Ollama, по умолчанию `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | имя модели, по умолчанию `llama3.2:1b` |
| `OLLAMA_KEEP_ALIVE` | сколько держать модель в памяти, по умолчанию `15m` |
| `SUPABASE_URL` | адрес проекта Supabase |
| `SUPABASE_SERVICE_ROLE_KEY` | служебный ключ Supabase, только на сервере |
| `SYNC_SECRET` | защищает маршрут выгрузки данных |

Ни одна переменная не имеет префикса `NEXT_PUBLIC_`, поэтому ни один ключ физически не может попасть в код, который выполняется в браузере. Для чата ключи не нужны вовсе: у Ollama нет платного доступа.

## Необязательные функции

### Чат с персонажами

Виджет на странице персонажа ведёт разговор от его лица. Системная подсказка собирается из настоящих данных: факультет и его черты, происхождение, палочка, патронус, годы жизни, роль в школе. Ответ приходит потоком, буква за буквой.

Модель запускает Ollama. Ключей и учётных записей не требуется.

**Локально.** Установите [Ollama](https://ollama.com) и загрузите модель:

```bash
ollama pull llama3.2:1b
```

Больше ничего делать не нужно: приложение по умолчанию ищет Ollama по адресу `http://127.0.0.1:11434` и использует модель `llama3.2:1b`.

**На сервере.** Всё поднимается одной командой, Ollama входит в стек:

```bash
docker compose up -d --build
```

Модель скачивается автоматически при первом запуске. Пока идёт загрузка, сайт уже работает, а виджет чата честно сообщает, что модель ещё в пути.

**Другая модель.** Любой тег из [библиотеки Ollama](https://ollama.com/library) подойдёт. Чем крупнее модель, тем точнее ответы:

```bash
OLLAMA_MODEL=qwen2.5:3b docker compose up -d
```

Если Ollama не запущена или нужная модель не загружена, приложение не ломается: маршрут отвечает кодом 503, а виджет показывает точную причину и готовую команду для исправления. Имя отвечающей модели видно в заголовке виджета.

### Лента в реальном времени

Пошаговая инструкция лежит в [`supabase/README.md`](supabase/README.md). Кратко: создайте проект, выполните `supabase/schema.sql`, укажите переменные, затем выгрузите данные командой

```bash
npm run sync
```

Страница `/live` покажет поток событий добавления в избранное от всех посетителей. Без настройки Supabase страница показывает не ошибку, а оформленную карточку с описанием функции.

## Процесс проектирования и разработки

**Шаг 1. Изучение источника данных.** До первой строки кода я запросил все конечные точки Harry Potter API и посчитал реальные распределения полей. Выяснилось важное: изображения есть лишь у 25 персонажей из 437, патронус указан у 18, а поле факультета пустое у 302. Эти три числа определили весь дальнейший дизайн: карточка обязана красиво выглядеть без портрета, фильтр по факультету обязан честно говорить о категории «без факультета», а строить интерфейс вокруг патронуса нельзя.

**Шаг 2. Каркас и общий язык.** Сначала были написаны только те модули, от которых зависит всё остальное: типы данных, серверный клиент API, данные о факультетах, тема оформления и базовые компоненты. Это дало единый визуальный язык до того, как появилась хоть одна страница, и избавило от последующей унификации разнородных экранов.

**Шаг 3. Параллельная разработка функций.** Приложение было разбито на восемь независимых срезов: главная, факультеты, каталог, карточка персонажа, заклинания с артефактами, избранное, лента Supabase и чат. Каждый срез владел строго своим набором файлов и не имел права трогать чужие. Общие модули были заморожены. Такое разделение позволило вести работу над всеми срезами одновременно без конфликтов слияния.

**Шаг 4. Проверка каждого маршрута.** Проверялись не только коды ответов, но и содержимое: страница Когтеврана обязана содержать Полумну Лавгуд, поиск по слову «hermione» обязан находить Гермиону, несуществующий факультет обязан отдавать 404. Отдельно проверялись состояния без ключей: чат, избранное и выгрузка данных должны деградировать мягко.

**Шаг 5. Приведение в порядок.** Production-сборка, проверка типов и стиля, разбор поведения кодов ответа, тест чата на настоящей локальной модели.

## Уникальные подходы и методологии

**Граница «сервер/клиент» защищена компилятором, а не дисциплиной.** Модули `lib/hp-api.ts`, `lib/supabase.ts` и `lib/ollama.ts` начинаются с директивы `import "server-only"`. Если кто-то попытается импортировать их в клиентском компоненте, сборка упадёт. Требование задания превращается из договорённости в проверяемое свойство: в браузерном коде есть ровно четыре сетевых вызова, и все четыре ведут на собственные маршруты приложения.

**Устойчивость к засыпанию внешнего API.** Harry Potter API размещён на бесплатном тарифе и после простоя просыпается долго. Ответы кешируются на час средствами Next.js, а в памяти процесса хранится последний удачный ответ. Если внешний сервис на минуту исчезнет, посетитель получит чуть устаревшие данные вместо страницы ошибки.

**Чистая функция поиска.** Фильтрация и разбиение на страницы вынесены в функцию `searchCharacters(all, query)`, которая не выполняет запросов и не зависит от окружения. Благодаря этому страница и маршрут API применяют буквально один и тот же код, и результат сервера всегда совпадает с результатом браузера.

**Состояние каталога живёт в адресной строке.** Поисковый запрос, факультет и номер страницы попадают в URL. Ссылку на выборку можно отправить другому человеку, кнопка «назад» работает предсказуемо, а первая отрисовка приходит с сервера уже с нужными данными.

**Реальное время без обращения браузера к чужому сервису.** Обычно живая лента Supabase подключается прямо из браузера, но это нарушило бы главное требование задания. Поэтому сервер сам следит за новыми строками, а страница получает их через собственный поток Server-Sent Events. Если поток дважды оборвётся, страница сама переходит на опрос раз в пять секунд.

**Языковая модель без внешнего сервиса.** Обычно чат с персонажем означает обращение к чужому API и платный ключ. Здесь модель работает на нашем же сервере под управлением Ollama, поэтому главное требование задания выполняется буквально: за пределы стека не уходит ни один запрос. Приложение не просто проверяет доступность модели, а различает две ситуации — Ollama не отвечает и модель не загружена — и показывает для каждой свою подсказку с готовой командой.

**Проверка фактами, а не отчётами.** Каждое утверждение о готовности подтверждалось запросом к работающему приложению. Например, вывод о кодах ответа сделан не по памяти, а после сравнения поведения двух похожих маршрутов и чтения документации установленной версии фреймворка.

## Компромиссы

**Пагинация вместо бесконечной прокрутки.** Задание разрешало любой из двух вариантов. Пагинация выбрана потому, что номер страницы помещается в URL и делает выборку разделяемой ссылкой, а также остаётся доступной с клавиатуры и для программ чтения с экрана. Цена решения: листать длинный список чуть менее удобно.

**Фильтрация на стороне сервера, а не в базе.** Весь список персонажей помещается примерно в 180 килобайт и запрашивается один раз в час, поэтому поиск выполняется в памяти сервера. Для миллиона записей такое решение было бы неверным, но здесь оно избавляет от лишней инфраструктуры и даёт мгновенный ответ.

**Артефакты хранятся в коде.** У Harry Potter API нет раздела артефактов, а задание требует их показать. Данные о 23 предметах выверены по книгам и лежат в `lib/artifacts.ts`. Компромисс осознанный: за точность отвечает репозиторий, а не внешний источник, зато раздел не зависит от чужого сервиса.

**Заклинания фильтруются в браузере.** Их всего 77, и они приходят вместе со страницей. Поиск получается мгновенным, без единого запроса. Маршрут `/api/spells` при этом существует для программного доступа.

**Отказ от файла загрузки в разделе персонажей.** Ради корректного кода ответа 404 пришлось убрать промежуточный экран загрузки для карточки персонажа. Подробности в следующем разделе.

**Локальная модель вместо облачной.** Облачный провайдер дал бы заметно более умного собеседника без всякой возни с загрузкой весов. Выбрана Ollama, потому что она не требует платных ключей, полностью снимает вопрос об утечке учётных данных и делает требование о серверных вызовах не декларацией, а фактом. Цена решения — ответы небольшой модели менее точны, а образ занимает больше места на диске.

**Supabase и чат не обязательны.** Можно было сделать их непременным условием запуска, но тогда проект нельзя было бы просто склонировать и открыть. Вместо этого каждая такая функция определяет своё состояние сама и объясняет, как её включить.

**Интерфейс на английском, документация на русском.** Данные приходят на английском, и смешение языков в карточке персонажа выглядело бы неопрятно.

## Известные проблемы и ограничения

**У большинства персонажей нет портретов.** Изображения есть только у 25 записей из 437. Для остальных карточка показывает инициалы на фоне цветов факультета. Это свойство источника данных, а не ошибка приложения.

**Внешний API просыпается медленно.** Первый запрос после долгого простоя может занять до полуминуты. Кеш и хранение последнего удачного ответа сглаживают проблему, но самый первый заход после развёртывания бывает медленным.

**Маленькая модель выдумывает подробности.** Модель по умолчанию `llama3.2:1b` весит чуть больше гигабайта и хорошо держит образ персонажа, но факты искажает. В проверочном разговоре Гарри верно назвал патронуса оленем, однако приписал свою палочку Артуру Уизли, хотя в системной подсказке указаны настоящие материалы. Помогает более крупная модель, например `qwen2.5:3b` или `llama3.1:8b`, но ей нужно больше памяти. Это ограничение размера модели, а не ошибка кода.

**Первый ответ после простоя приходит с задержкой.** Ollama выгружает модель из памяти, и следующий запрос ждёт её загрузки. Параметр `OLLAMA_KEEP_ALIVE` со значением 15 минут смягчает это, но первый разговор после долгой паузы начинается медленнее. На процессоре ответ из нескольких предложений занимает от пяти до пятнадцати секунд, поэтому он и приходит потоком, а не целиком.

**Чат требует ресурсов сервера.** Модель считается на процессоре той машины, где запущена Ollama. Для модели на миллиард параметров достаточно примерно двух гигабайт памяти, для более крупных нужно больше. На бессерверных платформах вроде Vercel такой контейнер запустить нельзя, поэтому чат доступен только при развёртывании через `docker compose`.

**Разное поведение кодов ответа у разных разделов.** Несуществующий факультет отдаёт 404 на уровне маршрутизации, поскольку список факультетов известен заранее. Для персонажей заранее известного списка нет, поэтому 404 формируется при отрисовке. Чтобы код ответа был настоящим, а не подменённым на 200, из раздела персонажей убраны файлы `loading.tsx`: любой экран загрузки начинает отдавать ответ раньше, чем становится известно о существовании записи, а после начала передачи код ответа изменить нельзя. Каталог сохранил свой скелетон через собственную границу ожидания внутри страницы.

**Лента реального времени опрашивает базу, а не подписана на неё.** Сервер проверяет новые события раз в две секунды, поэтому задержка составляет до двух секунд. Прямая подписка из браузера была бы быстрее, но нарушила бы требование о серверных вызовах.

**Соединение с лентой обрывается каждые пятьдесят секунд.** Так сделано намеренно: бессерверные платформы ограничивают время жизни запроса. Браузер переподключается сам, разрыв не виден.

**Папка проекта не должна лежать в синхронизируемой облаком директории.** На macOS Рабочий стол по умолчанию синхронизируется с iCloud. Служебная папка сборки `.next` весит сотни мегабайт, и облако начинает создавать в ней конфликтные копии вида `routes.d 2.ts`, из-за чего сборка зависает, а проверка типов падает на дубликатах. Если проект лежит в `~/Desktop` или `~/Documents`, перенесите его, например в `~/Projects`, либо отключите синхронизацию этих папок.

**Тесты не написаны.** Проверка велась через запросы к работающему приложению, проверку типов и линтер. Автоматических тестов в проекте нет, и при дальнейшем развитии их стоит добавить в первую очередь для функции `searchCharacters`, которая для этого специально сделана чистой.

## Деплой

Чат нуждается в постоянно работающем процессе Ollama, поэтому приложение рассчитано на хостинг контейнеров, а не на бессерверные платформы.

### Рекомендуемый способ: docker compose

Подходит для любого VPS, а также для Railway, Render, DigitalOcean и Fly.io.

```bash
git clone https://github.com/msultans/harry-potter-explorer.git
cd harry-potter-explorer
docker compose up -d --build
```

Поднимаются два сервиса: приложение на порту 3000 и Ollama во внутренней сети. Модель скачивается один раз в именованный том `ollama-models` и переживает перезапуски. Наружу Ollama не публикуется, обращаться к ней может только приложение.

Полезные команды:

```bash
docker compose logs -f app          # логи приложения
docker compose logs -f model-puller # ход загрузки модели
docker compose down                 # остановить
docker compose down -v              # остановить и удалить скачанную модель
```

Порт меняется переменной `PORT`, модель — переменной `OLLAMA_MODEL`.

Что стоит знать заранее:

| Параметр | Значение для настроек по умолчанию |
|---|---|
| Образ `ollama/ollama` | около 7 ГБ на диске |
| Модель `llama3.2:1b` | 1,3 ГБ, скачивается один раз в том |
| Память | примерно 2 ГБ на модель плюс около 200 МБ на приложение |
| Первый ответ | 5–15 секунд на процессоре, дальше быстрее |
| Развёрнутый стенд | Hetzner CX22: 2 ядра, 3,7 ГБ, занято 2,2 ГБ и 16 ГБ диска |

Модель считается на процессоре, видеокарта не нужна. Ollama наружу не публикуется: в списке портов у неё нет привязки к хосту, обращаться к ней может только приложение по внутренней сети.

Скрипт `deploy/hetzner.sh` делает всё это за один заход: проверяет доступ по SSH, ставит Docker, копирует проект и поднимает стек.

```bash
./deploy/hetzner.sh root@IP-адрес           # по HTTP на порту 80
./deploy/hetzner.sh root@IP-адрес my.domain # с HTTPS через Caddy
```

Повторный запуск обновляет уже развёрнутое приложение.

### Без Ollama

Если сервер не тянет модель или нужен бессерверный хостинг вроде Vercel, приложение разворачивается обычным образом и работает полностью, кроме чата: виджет покажет, что модель недоступна, а все остальные разделы останутся рабочими. Отдельно стоящую Ollama можно подключить, указав `OLLAMA_BASE_URL`.

Для этого случая в корне лежит `Dockerfile`, а сборка настроена в режиме `standalone`:

```bash
docker build -t harry-potter-explorer .
docker run -p 3000:3000 harry-potter-explorer
```
